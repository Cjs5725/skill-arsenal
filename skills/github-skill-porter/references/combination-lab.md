# 组合实验台：技能拆解与重组规则（N → 单元 → 新技能）

> 定位：`merge_skills.py` 的反方向。合并是**去重**（同能力多配置收敛，不造新性质）；
> 组合是**造新性质**（跨能力单元拼出新用户目标）——两者准入闸相反，产物永远分开记账。
> 脚本：`scripts/decompose_skills.py`（拆）、`scripts/compose_skill.py`（合）。

## 一、可行性边界（先说清什么能组合、什么不能）

| 层 | 可组合性 | 说明 |
|---|---|---|
| 方法论 / 判据 / 清单（SKILL.md 正文单元） | **可组合** | 组合稿的主体；单元是文字判据，拼入新语境即可生效 |
| 包内资源（references/scripts/assets 文件） | 可随迁 | 单元正文引用的包内文件必须随组合稿搬迁，否则悬空引用（实测 goldie 单元触发） |
| 脚本级功能（跨技能代码互调） | **不可组合** | 不保证兼容，组合稿不承诺脚本互通；需要脚本能力时按原技能独立安装 |
| 判据互相矛盾的组合 | 不可组合 | 由人工终审把关，门禁只拦结构，拦不住语义冲突 |

## 二、拆解规则（decompose_skills.py）

1. **粒度**：SKILL.md 的二级标题段（`## …`）为一个单元——过细则碎、过粗则黏连；
2. **类型四分**：capability（能力正文）/ workflow（执行流程）/ boundary（边界与降级）/ qa（质量自检）；
3. **排除**：搬运说明段（出处信息非能力）、frontmatter（字段层）不入库；
4. **自含性**：正文命中「上一节/如上所述/见第 X 节」者标 `self_contained=false`，组合闸拒绝不自含单元；
5. **强制溯源**：每单元带 `skill + 源行号`，组合稿逐节标注来源，出处表收尾。

## 三、组合规则（compose_skill.py，三道硬闸 + 一道资源闸）

1. **目标先行闸**：goal ≥ 20 字的**单一用户目标**，先定义目标再选单元——禁止先拼后想（组合出弗兰肯技能的主因）；
2. **单元存在闸**：每个 (skill, section) 必须命中单元库且 self_contained，且必须写明**在新目标下的角色**；
3. **判据完备闸**：组合级 boundaries ≥ 2 条、组合级 qa ≥ 2 条——组合引入的新风险（口径冲突、降级路径）必须显式成文，防通用套话骨架；
4. **资源随迁闸**：单元正文引用的 `references|scripts|assets/...` 文件从源技能自动搬迁进组合稿；
5. 组合稿版本固定 `0.1.0`、author 标「WorkBuddy 组合实验台」、正文首部带组合声明，**整体定位是草稿**：双门禁通过 ≠ 可上架，上架前必须人工终审（语义冲突只有人能判）。

## 四、实测锚点（2026-09-22）

- 拆解：22 技能 → **212 单元**（capability 146 / workflow 22 / boundary 22 / qa 22），搬运说明 22 段排除，不自含 0；
- 组合三例全部通过双门禁（self_check 0 issues + 中文化 PASS）：
  - `listing-material-suite`（5 单元 / 3 技能：catalog-listings + goldie + theme-factory）——
    **门禁实战拦截 2 处悬空引用**（goldie 单元引用其 references/config.md 与 flows.md），
    由此催生资源随迁闸——规则不是预设的，是被产物逼出来的；
  - `ops-morning-brief`（6 单元 / 3 技能：inventory-operations + performance-insights + pricing-promotions）；
  - `care-grounded-reply`（4 单元 / 3 技能：customer-care + commerce-trust-safety + memory-personalization）；
- 产物与规格存档：`_release/2026-09-22/combination-lab/`（草稿 + composition-spec.json 可复现）。

## 五、与合并引擎的分工

| | merge_skills.py（合并） | compose_skill.py（组合） |
|---|---|---|
| 输入关系 | 同能力、高相似（≥ 阈值） | 跨能力、目标统一 |
| 产物性质 | 去重收敛，不造新性质 | 造新性质，草稿待审 |
| 验收核心 | 零丢失（逐行覆盖率 100%） | 三闸一资源 + 人工终审 |
| 记账 | 不入组合台账 | 入组合台账（combination-lab） |

## 六、语义终审最小清单（人工/LLM 终审必过三查，2026-09-25 定稿）

> 背景：三闸一资源闸只管结构，**语义冲突只有审能拦**。三例组合稿（09-22）因此悬空——
> 悬空的验收＝事实上的不验收，故定此最小清单：终审要么审掉、要么显式冻结，不允许挂着不管。
> 状态记账：`_release/<日期>/combination-lab/终审台账.md`（逐稿一行，状态只允许：已审 PASS / 已审 FAIL+原因 / 冻结待需求驱动）。

| # | 检查项 | 查什么 | 方法 | 通过标准 |
|---|---|---|---|---|
| 1 | **判据互斥检查** | 所选单元对同一事项的规定有无互相矛盾（不同来源技能的口径冲突，如两套降级规则、两种命名规范） | 逐对比对单元正文中出现同类规定的段落 | 无矛盾，或矛盾已由组合级 boundary 显式裁决（「以 X 为准，Y 并列呈现」） |
| 2 | **目标偏离检查** | 每个单元在新目标（goal）下是否必要、是否引入无关行为——组合稿最大的病是「顺手多带」 | 对每个单元问一句「删掉它，目标还成立吗」 | 每单元都有不可替代的角色；答案含糊的单元直接删 |
| 3 | **语境适配检查** | 单元正文里的示例、路径、角色设定、平台专名在新技能语境下是否成立 | 扫残留旧技能专名 / 失效路径 / 假设性前提 | 无残留专名；残留即改写或删除 |

三查全过 → 终审 PASS，草稿可进上架评估；任一不过 → FAIL 记原因，或整体标注「冻结待需求驱动」（无真实需求时不投入终审工时，但必须写进台账，不得悬空）。
