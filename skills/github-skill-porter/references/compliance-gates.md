# 合规门禁与多源接入 SOP

本文件承载 SKILL.md「能力 9 / 10 / 11」的细则。**做合规判定、去毒处置、非 GitHub 源接入时读本文件。**

---

## 一、许可准入：两道具门

### 1.1 为什么需要两道具门

「**能否搬运**」与「**能否对外分发（上架）**」是两个不同的问题，混在一起就会出现"字段填对了但形式上不合规"或"评分宽容被误用到准入红线"。

法律基线：《伯尔尼公约》与中国《著作权法》下，作品**自创作完成即受保护**——不需要登记、不需要声明。GitHub 上不写 LICENSE 的仓库 = **保留所有权利**，默认禁止复制、修改、分发。因此**无 LICENSE ≠ 可自由复制**；复制 + 分发本身即构成侵权，**民事上不以营利为前提**。

刑事是另一层：《刑法》第 217 条为**目的犯**（"以营利为目的"），且需违法所得 ≥ 3 万、或非法经营额 ≥ 5 万、或复制品 ≥ 500 份。所以"有收入才够得着刑事"是准的——**但那不是安全垫，是时间差**，而时间差不是权利基础。

### 1.2 分级与处置

`classify_license(spdx)` 把 SPDX 归为三级：

| 级别 | SPDX | 处置 |
|---|---|---|
| `permissive` | MIT / Apache-2.0 / BSD-2 / BSD-3 / ISC / 0BSD / Unlicense / CC0-1.0 / Python-2.0 / MulanPSL-2.0 / MPL-2.0 / CC-BY-4.0 | **双轨**：出本地版 + 平台版 zip；**强制随包 LICENSE 全文与归属声明** |
| `copyleft` | GPL-2.0 / GPL-3.0 / **AGPL-3.0** / LGPL-2.1 / LGPL-3.0 | **仅本地版**：不生成上传包，改动清单标注"不得对外分发" |
| `unknown` | 未识别 / 无 LICENSE | **默认拒收**（报错并非零退出）；`--allow-restricted` 放行后仅本地版 + 强制风险标注 |

### 1.3 识别顺序（易错点）

`AGPL-3.0` 的匹配**必须排在 `GPL-3.0` 之前**。AGPL 全文为 "GNU AFFERO General Public License"，若被误判为 GPL，会漏掉第 13 条的部署义务——**AGPL 的义务重得多，误判即踩线**。

### 1.4 AGPL 第 13 条的精确触发条件

原文前提是 `if you modify the Program`。触发条件 = **「修改」+ 通过计算机网络对外提供交互服务**，**不是"部署"本身**——原样部署不产生新的第 13 条义务。但实务上按最保守口径处理，原因有二：

1. 商业差异化几乎必然要改，而"我从未修改过"极难自证（改配置、加适配层、打补丁、插件动态加载都可能被主张为修改或衍生作品）；
2. **"给客户私有化部署"也算对外提供服务**（不是本公司员工使用即触发）。

### 1.5 许可随包（分发形式合规）

`write_license_bundle()` 生成两件：

- `LICENSE` —— 源许可全文（取自源目录 LICENSE / 仓库根 LICENSE / `SOURCE_INFO.json` 的 `license_text`）
- `THIRD-PARTY-NOTICES.md` —— 来源 / 来源类型 / 源规格 / SPDX / 生成时间 / 许可文本位置

依据：Apache-2.0 第 4(a) 条（向接收副本者提供许可副本）、第 4(c) 条（保留版权与归属声明）；MIT / BSD 同类义务。**缺这一步，即便 SPDX 识别正确，分发形式上也不合规。**

本地版若原目录无许可文件，同样补写 `LICENSE`——不让本地版成为无许可副本。

### 1.6 边界（必须说清）

这是**工程侧的形式合规，不是法律意见**。"是否构成侵权"是**事实判断**——票数、评分、工具结论都不能覆盖它。筛选环节可以宽容（提示风险、不埋没候选），**准入环节必须逐条卡死**。商业化签字前须由执业律师复核。

## 二、去毒审计规则摘要

技能是**可执行代码**，拥有与 Agent 相同的权限（读文件系统、读环境变量、执行 Shell）。本工具"刮取谁都会、净化不是"里的净化即指此。

### 2.1 已公开实测数据（二手，供判断严重性）

| 数据 | 来源 |
|---|---|
| ClawHub 341 个恶意技能分发 macOS 恶意软件（ClawHavoc） | dev.to 综述 |
| ClawHub 全量扫描 **7.1%（283 个）** 技能源码硬编码 API Key | Snyk ToxicSkills |
| 1,200+ 技能排查：341 个恶意（11.3%），**36% 含提示词注入** | 腾讯新闻引研究 |
| 22,511 个技能审计：140,963 个问题（平均 6.3 个/技能） | Agensi 引审计 |
| MCP 生态 60 天 30 个 CVE，**82% 路径遍历**，38% 无身份认证 | 腾讯新闻 |

### 2.2 六类规则与分级

`scan_toxicity.py` 共 **35 条规则 / 6 类**：

| 类别 | 典型命中 | 级别 |
|---|---|---|
| **凭据泄露** | Anthropic / OpenAI / GitHub / AWS / Google / Slack / Stripe 密钥、私钥文件、JWT；`api_key = "…"` 赋值形式 | 密钥 hard；JWT 与泛化赋值 review |
| **提示词注入** | `ignore previous instructions`、`忽略以上指令`、`do not tell the user`、身份覆盖、**Unicode 双向控制字符**（Trojan Source）、注释内隐蔽指令、凭据外传 | 多为 hard |
| **危险执行** | `rm -rf /`、`curl … \| sh`、base64 解码后管道执行、反弹 shell（`/dev/tcp/`、`nc -e`）、`subprocess(..., shell=True)` | 前四者 hard；`eval`/`exec`/`os.system`、`chmod 777` review |
| **敏感读取** | `~/.ssh/id_*`、`authorized_keys`、`.aws/credentials`、`.config/gcloud/`、`.docker/config.json` | hard |
| **路径遍历** | `../../../`、带上级路径的文件读取 | review |
| **供应链** | 非 HTTPS 源安装、未锁定版本、`npx` 拉取远端包 | 非 HTTPS hard；其余 review |

### 2.3 分级处置与去噪

- `hard` —— 与结构硬问题**同等待遇**：阻断交付、**撤下已生成的上传包**、退出码非 0。**不去噪**，每一处都须逐条修复。
- `review` —— 列入"待人工确认"，须逐条判定后才可上架，**不得把"待确认"当"已通过"**。
- 结论写入各 `<slug>/porting-changes.md`「六」节与 `batch-report.md`「去毒」列。
- `review` 级按「同一文件 + 同一规则 + 同一证据」**去噪合并**并附出现次数（实测某技能的未固定版本包在正文重复 9 次，合并为 1 条）；`hard` 级不合并。

### 2.4 边界

**静态正则扫描，不是安全认证**：存在漏报（语义型后门、混淆载荷可能漏检）与误报（示例文本可能命中）。默认执行，`--no-security-scan` 可跳过——**跳过需在交付说明中写明理由**。

## 三、GitHub 之外的采集源接入契约

### 3.1 为什么需要契约

可采集的源不止 GitHub（网络数据平台、知乎类内容平台、技能市集、包注册表等）。生产端不应为每个新平台改代码，采集端也不应重复实现搬运逻辑——**中间用一份元信息契约对接**。

### 3.2 契约：`SOURCE_INFO.json`

采集方把素材交过来时，在**素材根目录**放一份可选文件：

```json
{
  "platform": "zhihu",
  "source_url": "https://example.org/article/123",
  "author": "某作者",
  "license": "Apache-2.0",
  "license_text": "Apache License\nVersion 2.0, January 2004\n…",
  "collected_at": "2026-09-14"
}
```

| 字段 | 作用 |
|---|---|
| `platform` | 来源平台标识（仅记录） |
| `source_url` | 来源地址，写入归属声明，便于回溯 |
| `author` | 作者，写入归属声明 |
| `license` | SPDX 标识，参与准入分级判定 |
| `license_text` | 许可全文；缺失时工具回落到源目录 LICENSE 文件 |
| `collected_at` | 采集时间（仅记录） |

### 3.3 行为约定

1. `load_source_info()` 读取该文件，据此完成归属与许可判定；
2. **该文件不进产出**（`plan_files()` 显式排除），其信息进 `THIRD-PARTY-NOTICES.md`；
3. 产出说明与报告按实际来源类型表述，**不写死 GitHub**；
4. 采集方声明的 `license` 属**自述**，工具据此判定但**不代为核验**——声明真实性由采集方负责。

### 3.4 边界

素材若为文章类内容（知乎回答、教程、公众号文），「素材 → SKILL.md」的**方法论提炼属语义层**，由 LLM 或人工按 SOP 完成；本工具负责其后的标准化、合规、打包与上架物料。

## 四、上架物料字段

`port_skill.py --listing` 生成 `<输出根>/listing/<slug>.md`：

| 字段 | 取值来源 |
|---|---|
| 标题（建议 ≤ 20 字） | `display_name` |
| 一句话简介 | `description_zh`；若为自动补的模板句则回落到 `description_en` 并标注"待运营层改写" |
| 原文摘要 | 正文第一段实质散文（跳过标题/列表/表格），供改写参考 |
| 分类 / 标签 | `category` / `tags`，缺则标注"待运营层确定" |
| 示例问法 | 正文中"当用户…/适用于…/触发词…"类句子，最多 5 条 |
| 上架前检查清单 | 固定模板：简介是否已改写、许可是否随包、等级是否 permissive、是否登记台账 |

**排除规则**：`copyleft` / `unknown` / 自检 FAIL / 强依赖的产出**不进上架物料**。

**不做语义**：本工具只做结构化提取，**不写文案、不做中文化**；润色与定稿属运营层职责。识别到模板化假简介（"将 X 技能迁移至 WorkBuddy…"）时回落并标注，**不伪造成稿交付**。
