# 合并与素材接入细则

> 本文承接 SKILL.md「能力 12 · N:1 合并」与「能力 10 · 采集源接入」的执行细节。
> 主文件只留判据与边界，实施步骤与失效模式放这里。

---

## 一、N:1 合并：为什么第一道工序是"拒绝"

合并的价值上限不在"合了多少个"，而在"能不能分辨哪些该合"。
把 N 个相似源塞进一个目录**不是合并，是堆叠**——它不会提升产能，只会制造一个
谁都读不懂的超长 SKILL.md。

所以 `merge_skills.py` 的第一道工序不是合并，而是**拒绝**：

| 闸 | 判据 | 不过的处置 |
|---|---|---|
| ① 相似度准入 | 两两正文相似度 ≥ 阈值（默认 0.80） | 判「不同能力」，**拒绝合并**，提示保持各自独立 |
| ② 许可一致性 | 成员许可一致 | 默认拒绝（混合许可会污染归属声明）；`--allow-mixed-license` 才放行 |
| ③ 零丢失验收 | 每成员正文**逐行覆盖率 100%** | 判失败，不落盘 |
| ④ 平台校验 | 官方 `validate_skill.py` 判「通过」 | 不出 zip |

**实测锚点**（第一批 22 个平台版）：

| 组合 | 相似度 | 结果 |
|---|---|---|
| `plus-astra-orchestrator` ↔ `pro-astra-orchestrator` | **0.974** | 通过（共同 441 行 / 差异 6 处 / 丢行 0） |
| `customer-care` ↔ `inventory-operations` | 0.395 | 拒绝 |
| `goldie` ↔ `theme-factory` | 0.128 | 拒绝 |

注意英文 vs 中文的差别不是障碍：astra 双子是**纯英文**技能，相似度照样 0.974。
相似度算的是行序列的 difflib 比值，与语种无关。

## 二、合并稿的三种表示（差异必须落纸）

给定基线成员 B 与其它成员 V，对 B 与每个 V 跑行级 diff：

| diff 类型 | 含义 | 落纸形式 |
|---|---|---|
| `replace` | 同一位置两侧取值不同 | 表「基线取值 / 该变体取值」 |
| `insert` | V 独有的新增行 | 列表「该变体独有的新增行」 |
| `delete` | B 有而 V 没有的行 | 列表「该变体不含的行」 |

三类记录合起来覆盖了两侧**全部**差异行——这是零丢失验收能够成立的前提。
合并稿正文只保留**各变体共同部分**；被替换/删除的行**已从共同正文剔除**，
所以变体表的左列叫「基线取值」而**不是**「共同部分取值」——标错会让读者
以为正文里同时存在两种写法。

## 三、合并稿的身份必须中性

合并稿**不得继承任何单一变体的身份**。初版踩过五个坑，都是实测出来的：

| 现象 | 后果 |
|---|---|
| `display_name` 仍是 "Plus Astra Orchestrator" | 拿到合并稿的人以为它只支持 Plus |
| `description_en` 仍写 "the Plus profile" | 平台用户**先读到的就是这句** |
| `display_name` 被派生为 **"不适用于"** | 注入的中文描述破坏了上游的名称派生正则 |
| `description` 出现两行「搬运来源」，首行指向单一变体 | 归属误导 |
| 英文描述里嵌直引号 | **YAML 标量提前闭合，解析必然失败** |

处置：显式赋中性名；描述前置 `This is a MERGED skill covering N variants of the same capability (...)`；
正则清理继承描述里的来源片段；生成文本里避免直引号（用 `「」`）。

## 四、合并 ≠ 组合（与 `COMBINATION_LAB` 的边界）

`COMBINATION_LAB.md` 铁律 3 规定「不填三要素的尝试，不得称为**新组合**」。
它约束的是"多个技能拼起来**产生新能力**"这类主张。

**N:1 合并是去重，不产生新性质**——astra 双子 445 行里 437 行相同，差异仅
"哪个模型扮演哪个角色"。合并它的目标性质是"无损失地收成一份"，判定方法是可机械
验证的零丢失，而非"新能力是否出现"。

**因此本能力不记入该台账。** 该台账第 4 节当前为空，且已声明阻塞项为
`HANDOFF.md Q-003`（卖什么服务品类未定）——该阻塞**不影响合并**，因为合并判定
不依赖"卖什么"。

## 五、扫描模式的复杂度约束

`--scan` 用并查集按阈值聚类（传递闭包，故组内两两可达），**复杂度 O(n²)**。

实测规模：一次采集批次可含数千个技能源（单仓 3596 个 SKILL.md）。
**数千源不可全量两两扫**，须先按来源或关键词缩小候选集，再对组内扫描。

第一批 22 项扫描结果：**1 组可合并（2 项）+ 20 项独立**。

## 六、与"打包/技能集"的关系（一处更正）

工具初版文案写过"应改用打包(pack)"，**这是越界表述**：项目各会话文档里
**没有「pack / 技能集」的既有定义**。

现口径：相似度不足者应**保持各自独立**；是否以「技能集」形式组织，
**取决于平台侧是否存在该承载形式，而这一点尚未验证**——属出口验证范围（运营端），
不在生产端职责内。**工具不假设它存在。**

## 七、采集源接入：契约有两级粒度

`P-0005` 契约最初只声明了**技能级**素材根（一个技能一个根，含 `SKILL.md` + `SOURCE_INFO.json`）。
而采集端（采集端 `--material-out`）产出的是**仓库级**（一个候选仓一个根，只有契约文件、
无 SKILL.md、`license_text` 为空——它"只写契约文件，不下载素材"）。
两者粒度不同，导致采集端产出**无法被生产端消费**。

修法（采集端**零改动**）：`--material-root` 解析 `<owner>__<repo>/SOURCE_INFO.json`
→ 探测文件树 → 展开为技能级源 → 下载 → 把仓库级的 `platform` / `source_url` /
`author` / `license` / `collected_at` **继承**给每个技能 → 落进归属声明。
`--material-limit N` 限制每仓取样数（大合集先小样本验证链路）。

**归属可追溯的实测输出**：

```
来源 | mohitagw15856/pm-claude-skills/exports/openclaw/360-feedback-template
      （采集平台 smithery；https://github.com/mohitagw15856/pm-claude-skills；采集于 2026-09-15）
```

没有这一步，采集端投喂的信息虽然进了流程，却在交付物里**看不见**——
出了许可问题无从回溯"这条素材是哪次采集、从哪个平台来的"。

**实测规模**（一次采集的 5 个仓库级素材根）：

| 仓库 | 采集平台 | 许可 | 展开技能源数 |
|---|---|---|---|
| `alibaba/open-code-review` | gh-trending | Apache-2.0 | 4 |
| `JustVugg/colibri` | gh-trending | Apache-2.0 | 0（无 SKILL.md，属「需创作技能」） |
| `mohitagw15856/pm-claude-skills` | smithery | MIT | **3596** |
| `NEAT-Technologies/Neat` | npm | Apache-2.0 | 2 |
| `Pandemonium-Research/Skilldex` | npm | MIT | 21 |
| **合计** | | | **3623** |

**3623 个技能源来自一次采集。** 这既是"高产能"的字面含义，也说明瓶颈不在
"能不能搬"，而在"**搬来的东西怎么收敛**"——同能力多配置只是其中一种收敛方式。

## 八、自检不能替代平台门禁（一条硬教训）

平台校验器的三条结构正则是**纯中文词**（`边界|降级|兜底|异常|不适用|禁止` 等），
**英文源技能必然不命中**。而 `port_skill.py` 的自检原本不含此项。

后果：自检判 PASS 的 21 个产出，被平台校验器**全部判 FAIL**（缺「边界与降级」「质量自检」），
却被列进了上架清单——**清单说谎**。

处置：① 自检纳入与校验器**同一套正则**的结构检查，面向平台上传的产出必须保留该检查
（仅本地自用产出放宽）；② 生产时**调用官方校验器独立复核**，结论写入
`batch-report.md` 与上架物料；③ 上架清单只收「平台校验通过」的产出。

**骨架 ≠ 内容**：`--ensure-sections` 补的是带「须按源技能内容改写」标注的通用骨架。
补完后**结构合规、内容待夯实**，不能当成已完成品交付。
