# 中文化改写 SOP（平台版正文与字段）

> 适用：源技能正文为英文、或需面向中文用户交付时的平台版中文化。
> 定位：本步骤属**语义层**，由 LLM 或人工执行。`port_skill.py` 只负责结构转换与字段占位（自动推导的 `display_name` / `description_zh` 偏通用），**不承担翻译**。
> 前置：先跑完 `port_skill.py`（字段补全 / 引用重写 / 许可识别 / 自检门禁），再在平台版产物上原地中文化；改完**必须复跑**门禁。

---

## 一、译什么

1. 正文全部标题、说明段落、步骤、判据、检查清单项。
2. 资源清单类描述文字（如「可用主题」「文件说明」）。
3. `references/` 下资源文件的说明性正文（主题名注解、适用场景等）。
4. frontmatter：`display_name`、`description_zh`（并按需润色 `display_name_en` / `description_en`）。

## 二、不译（原样保留）

| 类别 | 示例 | 处置 |
|---|---|---|
| 代码 / 命令 / 变量名 | `from core.gif_builder import` | 原样 |
| **包内**资源引用（`references/`、`scripts/`、`assets/`） | `references/themes__ocean-depths.md` | 原样，且必须与搬迁后真实路径一致 |
| **上游仓库**位置（本包不交付） | `commerce_common/prompt_assembly.py` | **不得写成路径形态**，见下方「上游仓库位置的写法」 |
| YAML 字段名 | `display_name`、`allowed-tools` | 原样 |
| 十六进制色值 | `#1a2332` | 原样 |
| 字体名 | `DejaVu Sans Bold` | 原样 |
| 专有名词 / 产品名 | `WorkBuddy`、`Slack` | 原样，或「中文（English）」并置 |
| 占位符 / 模板变量 | `{{...}}`、`<slug>` | 原样 |

### 上游仓库位置的写法（硬规范，2026-09-16 定）

**规范**：上游仓库（参考实现）内的模块与文件，一律写作「**上游 `<模块>` 包中的 `<文件名>`**」，
**不写** `模块/文件.py` 这种路径形态。

- ✅ 上游 `commerce_common` 包中的 `prompt_assembly.py`
- ❌ `commerce_common/prompt_assembly.py`

**为什么**：在包内裸写路径形态，读者会合理地理解为「**本包随附的文件**」，而它并不随包交付。
另有一个具体后果：`scripts/` 是**平台保留目录名**（官方校验器原文「平台仅识别 references/scripts/assets」），
裸写 `scripts/xxx.py` 会被官方校验器判 **FAIL**。

**信息不能丢**：正文开头统一声明目录映射，例如
「本文所有模块与文件均指上游参考仓库内的位置，不随本包交付；其中 `commerce_common` 对应上游
`commerce-common/commerce_common/`…… 下文凡写作「X 包的 Y」者，均指上游仓库中该模块下的同名文件。」

**上一版这句话为什么必须改**：旧文本写的是「文件路径与引用 → **原样**」，
在 `theme-factory` 那种「引用确实随包交付的资源」场景下是对的，
但对「上游仓库位置」不适用——两者必须分开。曾有 5 项因沿用旧口径而在宽口径门禁下报
2 / 17 / 23 / 25 / 26 处悬空引用，按本规范改写后**全部归零且信息无丢失**。

### 同时命中的四道检查（先量清命中面，再判断是真缺陷还是口径噪声）

| 检查 | 口径 | 对上例（`commerce_common/xxx.py`） |
|---|---|---|
| 官方 `validate_skill.py` | 只认 `references\|scripts\|assets/` 前缀 | 不命中 |
| `port_skill.py` 自检 | **同上口径** | 不命中 |
| 中文化门禁 `PATHISH` | 任何「目录＋含扩展名」的路径 | **命中**（宽口径噪声） |
| 全批一致性扫描 | 同官方口径、逐项跑 | 不命中 |

**判据**：命中面越宽，越可能是**真缺陷**。`scripts/check.py` 是唯一被**四道同时命中**的一处 → 真歧义，必须改；
其余 12 处同族路径只被宽口径那一道命中 → 按本规范改写法即可，**不必也不应改门禁**。

## 三、术语与并置规范

- 主题名、专有概念**首次出现**用「中文（English）」，如 `Ocean Depths（深海）`。
- 色名用「英文名 + 中文」，如 `Deep Navy 深海军蓝：`#1a2332``。
- 保持与源一致的章节层级与编号，**不增删章节**；源缺失的必备段落（执行流程 / 边界与降级 / 质量自检）用 `--ensure-sections` 骨架补写为**具体步骤与判据**，不留占位。

## 四、交付判据（中文化后必须复跑）

- [ ] 合规校验零 FAIL（官方 `validate_skill.py`）。
- [ ] 交付前自检双向引用：无悬空引用；搬迁的资源文件若按目录整体引用，正文需给出**可核对的路径索引**（否则触发「未被正文引用」警告）。
- [ ] **上游引用已按第二节规范改写**：全文不存在「模块/文件.py」形态的上游路径，且开头已声明目录映射。
- [ ] **`--ensure-sections` 补的骨架已按源技能内容重写**：不留「按源技能定义的核心动作依次执行」这类通用套话。
      （反例：`commerce-prompt-caching` 的 EN 平台版曾长期带着三段骨架占位交付，直到 2026-09-16 才被发现改写。）
- [ ] **保留中文段标题**：平台结构判据（`步骤|流程|工作流`／`边界|降级|兜底|异常|不适用|禁止`／`自检|检查清单|质量|验收`）
      **只认中文词**——这正是 `--ensure-sections` 存在的根本原因。EN 版正文可英文，但段标题须保留中文。
- [ ] 全中文正文无中英夹杂的整句；保留项均为上表所列类别。
- [ ] YAML 无中文引号、无未转义冒号。
- [ ] ⚠ **覆盖率分母陷阱**：覆盖率的分母是**当前文本**——把正文删短会让分母缩小、覆盖率虚高。
      故必须同时看**正文体量**（行数 / 中文字数）：说「译完了」要能拿出体量增长的数字
      （例：`commerce-prompt-caching` 92 行 / 322 字 → 119 行 / 2,965 字）。

## 五、样例（theme-factory）

- 正文标题 `# Theme Factory Skill` → `# 主题工厂（Theme Factory）`。
- 章节 `Purpose` → `用途`；`Usage Instructions` → `使用步骤`；`Themes Available` → `可用主题`。
- 资源引用 `theme-showcase.pdf` → `assets/theme-showcase.pdf`；`themes/ocean-depths.md` → `references/themes__ocean-depths.md`。
- 补写「执行流程 / 质量自检」段（源缺失），落为具体步骤与判据。
- 交付位置：平台版目录 + `<slug>-zh.zip`（root 直铺）；上传**必须用 zip**，不得含 `porting-changes.md` 等内部文档。

## 六、与脚本的分工

- `port_skill.py`：结构转换、字段补全、引用重写、许可识别、自检门禁——**先完成，再中文化**。
- 中文化：在平台版产物上原地改写，**不改变引用语义**，路径索引须与搬迁后真实文件名一致。
- 中文化完成后：重跑合规校验 + 自检门禁；重打上传 zip（纯技能内容）。
