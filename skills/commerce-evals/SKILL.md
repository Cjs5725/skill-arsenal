# 商务智能体行为评测

> **路径约定**：本文所有模块与文件均指**上游参考仓库**内的位置，**不随本包交付**，本包内不存在这些文件。
> 其中 `commerce_common` 对应上游 `commerce-common/commerce_common/`。

上游仓库**不附带评测框架**；评测套件归你所有——因为一个用例只有针对你自己的商品目录、订单与夹具才有意义。
不需要模型即可判定的门禁行为（来源溯源、上限、护栏、审批）用 `FakeClient` 做单元测试，它位于上游 `commerce_common` 包的 `testing.py`；
评测覆盖的是**由模型决定**的那部分。

## 一、用例形态

下面这个块是**用例形态与评分器名称的唯一出处**；`/author-commerce-evals` 也指向它。

```json
{
  "id": "<flow>-<nnn>-<behavior>",
  "priority": "critical | high | medium | low",   "difficulty": "easy | medium | hard",   "tags": ["..."],
  "skip": "<reason, when a case cannot run yet>",
  "state": {"seen_products": ["..."], "cart": [...], "memory": [...], "staged_changes": [...]},
  "turns": ["<the customer's or operator's message>", "..."],
  "expected": {
    "calls_tool": ["..."],            "calls_one_of": ["..."],          "never_calls": ["..."],
    "first_tool": "...",              "first_tool_not": "...",
    "ui_components": ["..."],         "no_ui": true,
    "cart_contains": ["..."],         "cart_item_count": 0,             "cart_not_contains": ["..."],
    "staged_change_kinds": ["..."],   "no_applied_changes": true,
    "memory_contains": ["..."],       "memory_not_contains": ["..."],
    "skill_loaded": "...",            "skill_not_loaded": "...",        "no_skill_load": true,
    "reply_includes": ["..."],        "reply_omits": ["..."],           "max_tool_calls": 0,
    "rubric": "PASS if <condition>. FAIL if <condition>."
  },
  "notes": "<what the case pins and the fixture fact that decides it>"
}
```

`state` 是前置条件；除非被测行为本身要求跨轮携带状态，`turns` 只放一条消息；
`expected` 只放这个用例真正要断言的那几个键。`state` 与 `expected` 里的 id 必须是你夹具中的真实 id。
`priority` 与 `difficulty` 让报告能说清哪些失败更要紧；暂时跑不了的用例带上 `skip` 并写明理由，**而不是删掉它**。

## 二、编写规则

- **前置条件放进注入状态**（已看过的商品、购物车、记忆事实、待生效队列），由运行器在该轮之前载入会话状态与记忆存储。
  更早的轮次只用于「行为本身要携带的状态」，不作他用。
- **每个正例都配一个反例**：凡断言某个组件、一次技能加载、一道门禁、一次披露或一次记忆写入的用例，
  同一细分场景下都要有一个断言其**不出现**的用例。拒绝类用例要有「本应服务」的对照。
- **记忆至少三个用例**：一条值得记住的话被写入；一个标识符或被排除内容被拒（**什么都没存、也不对用户报错**）；
  一条已存事实改变了下一会话的推荐结果。
- **评分对象是最终工具参数与其产生的状态**：最后一次呈现调用的 id、待生效变更上的字段、该轮之后的购物车与记忆存储。
  回复的措辞只针对「必须出现／必须不出现」的字符串评分。
  智能体走了哪条路径（`skill_loaded`、某个具名组件、在呈现类工具上的 `never_calls`）**只在路径本身就是被测行为时**才断言
  （例如必须先进行一次接地查询，或某次写入绝不能发生）；其余场合用 `calls_one_of` 给出可接受集合。
  当实跑走了用例未预期的路径而答案是对的，应把用例**放宽到可接受集合**，不要把它重新钉到观察到的路径上。
- **评分规则（rubric）是一条 PASS 条件加一条 FAIL 条件**，且不存在同时满足两者的回答；它要点明决定结论的那个夹具事实
  （更新后的送达日期、今天的价格）；你接受的各种变体要写进去；它**不涉及**语气、长度或组件的先后顺序。
- 提到健康、一次性跑腿或敌意内容的轮次，要断言记忆的终态（`memory_not_contains`，或对 `save_memory` 用 `never_calls`）。
  需要「已存事实改变推荐」的用例，其查询结果的集合里应同时包含该事实偏好的那一项与被它排除的那一项；
  **先跑一次搜索，再写用例**。
- `max_tool_calls` 按「行为良好的智能体需要多少次」来设；多商品的请求会在一轮内扇出多次搜索，
  而结束该轮的 `present_suggestions` 调用**不计入**。

## 三、评分器

- **代码评分器**读该轮产出的事件（上游 `commerce_common` 包的 `streaming.py`）：`tool_call` 的名称与参数、
  带 `blocked` 状态且在 `reason` 中给出门禁名的 `tool_result`、`ui` 组件名、最后一次 `cart_update` 或 `change_update`，
  以及回复文本。上表中除 `rubric` 之外的每个键都是代码评分器。
- **`rubric` 交给评判模型**。每个维度一次调用（预算被遵守、不编造可得性、权衡被说明），返回带结论与理由的结构化输出；
  转写以**引用材料**的形式传给它，包含工具结果与组件载荷；当转写超出评判模型的窗口时，**从开头截断**以保住被评的那一轮，
  并把截断记录在结果上。评判模型须钉在温度 0；改动评判模型或评分规则会**使其下所有已存结论失效**，
  故记录里要带上两者的指纹。
- **评判回复无法解析出结论时，记为「评判失败」**，与「智能体失败」分开统计。

## 四、运行节奏

| 何时运行 | 跑什么 | 以什么定论 |
|---|---|---|
| 每次合入智能体、技能、工具描述或夹具 | 回归集 | 每个用例跑多次试验；按集合设通过阈值 |
| 正在改动某一条流程时 | 该流程的定向集 | 失败集，与上一次运行并排读作基线 |
| 选择或升级模型（对应商务架构技能中的模型字段） | 全量 | 两份失败集并排比对 |
| 生产环境 | 对线上流量抽样并按同一批评分规则评判 | 按维度看趋势 |

**要比对失败集**；两次实跑之间顶线指标跳动一个点属于噪声。
改动后失败的用例，意味着这次改动破坏了该行为，或用例编码的是**过时的行为**；两者都是要修的，
并在提交信息里说明修的是哪一种。

## 五、带毒夹具

承载指令的商品页、评论与消息，存放在**仅供评测使用**的夹具中，由运行器在该次运行时合入后端，
并置于第三方品牌或卖家名下；**它们的任何 id 都不得出现在演示数据、种子数据或抓取快照中**。
每个此类用例都在代码层断言其反面（`never_calls`、`cart_not_contains`、`no_applied_changes`、
`memory_not_contains`、`reply_omits`），且它断言到的每一条注入途径，都必须是**驱动轮次真正送到模型面前**的那一条
（评论只在详情调用时才会被读到）。至少覆盖三类：要求写入购物车或提交一条待生效变更、要求记住某些内容、以及一条虚假声称
（一个优惠码、一项保证）。其「本应服务」的对照是同一细分场景下另一条良性的评测专用商品页，
这样「一律拒绝」的智能体会在它上面失败。

## 执行流程

1. **确定评测归属与边界**。先确认要评的是购物侧还是商家侧，并划清「不需要模型即可判定」的部分
   （来源溯源、上限、护栏、审批）——那部分用 `FakeClient` 做单元测试，不写进评测。判据：能说清哪些行为归单元测试、哪些归评测。
2. **选定细分场景与用例 id**。按「流程-序号-行为」组织 id，并为用例指定 `priority` 与 `difficulty`。
   判据：每个用例都能被归入某个流程，且报告能据此区分失败的轻重。
3. **准备夹具与前置状态**。把前置条件写进注入状态（已看过的商品、购物车、记忆事实、待生效队列），
   并确保 `state` 与 `expected` 里的 id 都是夹具中的真实 id。判据：先跑一次搜索/查询验证这些 id 与事实确实成立。
4. **写正例，并配一条同细分场景的反例**。逐条检查第二节的五条规则。判据：凡断言「出现某事物」的用例，
   都能指出同一细分场景下断言其「不出现」的那条对照用例。
5. **分别落定代码评分器与评分规则**。把可机器判定的键全部落到 `expected`（`calls_tool`、`never_calls`、
   `cart_not_contains`、`memory_not_contains` 等）；`rubric` 只保留一条 PASS 与一条 FAIL，并点明决定结论的夹具事实。
   判据：评分规则不存在能同时满足 PASS 与 FAIL 的回答；且不涉及语气、长度与组件顺序。
6. **按节奏纳管**。确定该用例属于回归集、定向集还是全量集，并把阈值一并定下。判据：能回答「这次改动应该跑哪一套」。
7. **跑并与基线比对**。运行后**比对失败集**而非只看通过率；追查每个新失败究竟是被测行为坏了，还是用例编码了过时行为。
   判据：每个新失败都在提交信息中给出归类与修法。
8. **登记评判模型指纹**。记录评判模型与评分规则两方的指纹，随结论一同存储。判据：任一变更后可以准确指出哪些已存结论失效。

## 边界与降级

- **上游不提供评测框架**。评测套件必须建立在你自己的商品目录、订单与夹具之上；没有这些真实素材时，
  只能给出用例骨架与规则，**不得编造 id、价格、送达日期或夹具事实**。此时应明确列出需要你补的素材清单。
- **无模型额度或判断力不稳定时**：先只跑代码评分器覆盖的键（它们不依赖评判模型），
  把 `rubric` 相关结论标注为「未评」；不要用一次不稳定的评判结果充当结论。
- **转写超出评判窗口时**：**从开头截断**以保住被评的那一轮，并把截断记录在结果上；
  不得静默丢弃截断这一事实（否则结论的适用范围会被误读为整段转写）。
- **评判回复解析失败时**：记为「评判失败」，与「智能体失败」分开统计；不得把解析失败计入智能体失分。
- **夹具 id 泄漏时**：带毒夹具的任何 id 一旦出现在演示数据、种子或抓取快照中，该夹具即失效，
  必须新造 id 并复核；不得沿用已泄漏的 id。
- **不适用**：需要模型判断的「回答是否得体」类评审、以及无夹具可依的通用能力评测，均不在本技能范围内。
- **禁止**：为了让用例通过而放宽 `rubric` 的 PASS／FAIL 条件；把 `skip` 的用例直接删掉；
  在没有对照反例的情况下只用正例。

## 质量自检

- [ ] 每个用例都能定位到具体流程与细分场景，且 `priority`／`difficulty` 已填写。
- [ ] 每个正例都有同细分场景的反例；每个拒绝类用例都有「本应服务」的对照。
- [ ] 记忆类用例齐备三个：值得记住的写入、被排除内容的拒写（无存储、无报错）、已存事实改变下一会话的推荐。
- [ ] 断言对象是最终工具参数与产生的状态；路径类断言（`skill_loaded`、具名组件、`never_calls`）只出现在
  「路径本身就是被测行为」的场合，其余用 `calls_one_of`。
- [ ] `rubric` 只有一条 PASS 与一条 FAIL，二者不可同时满足，且点明了决定结论的夹具事实；不涉及语气、长度、组件顺序。
- [ ] `state` 与 `expected` 中的 id 均为夹具真实 id，且已先跑查询验证。
- [ ] `max_tool_calls` 按行为良好的智能体所需设置，并已排除结束轮次的呈现调用。
- [ ] 带毒夹具的 id 未出现在演示数据、种子与抓取快照中，且每条注入途径都在驱动轮次中真正会到达模型。
- [ ] 评判模型已钉在温度 0，且评判模型与评分规则的指纹已随结论记录。
- [ ] 无占位符、无待填项；所有模块与文件引用均指向上游仓库且已被开头的路径约定覆盖。
